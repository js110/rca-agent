# Feature 分析框架（提示词模板）

目标：验证功能是否真正交付了需求（对照 spec/issue 逐条验收），评估实现质量、边界覆盖与对既有系统的兼容影响。
核心失败模式：主路径能跑通就下「功能完成」结论——不验证边界、不核对需求清单、不看对旧行为的影响。

---

## 调查原则

### 一、先建立需求基线（不能凭感觉评估）

按以下优先级定位 spec 来源：
1. **commit message 里的 issue 引用**（`#123` / `Closes #45` 等）——优先，去取对应 issue 的验收要求
2. **PR 描述 + 关联 issue** 中明确的验收标准
3. **仓库里的 spec 文档**：`docs/`、`specs/` 下与分支名/功能名匹配的文件
4. 以上都没有 → 以 PR 描述 + 测试为基线，报告注明「无外部 spec，需求基线来自 PR 描述」

从找到的来源提取**验收标准清单**；逐条对照，每条给出：已实现 / 部分实现 / 未实现，并挂 spec 原文（issue 引用/描述原文/spec 文件:行号）。

### 二、按数据流走完整链路

- 新功能一定有 入口 → 逻辑 → 出口，三个位置都可能与描述不符
- 逐层检查：参数校验、中间变换、返回值语义
- **先找对偶路径**（同构的旧功能：列表 vs 详情、创建 vs 编辑、导入 vs 导出、A 模块 vs B 模块）对比行为——差异处是 feature 分析最容易出洞察的地方：旧路径有的校验/兜底，新路径缺了 → 直接怀疑

### 三、范围核查（Spec 轴）

对照需求基线，diff 里逐条核：
- **缺的**：spec 要求了但没实现/只做了一半的
- **多的（scope creep）**：diff 里出现但 spec 没要求的——单独列出，与需求覆盖分开评估
- **错的**：看似实现了但行为与 spec 不符的——必须指出具体差异（输入 → 期望输出 → 实际输出）

所有结论挂 spec 原文或「无 spec，以描述为准」。

### 四、边界与错误处理（必查清单，不是可选项）

- 空数据 / null / 非法输入 / 超长输入
- 重复提交 / 并发
- 权限、配置缺失、依赖服务不可用
- 新开关与旧功能的交互：新功能开启后旧路径是否被破坏

### 五、兼容性

- 公共 API / 数据结构是否变化，所有调用方是否同步更新
- 存储格式是否变化：旧数据能否被读取、新旧版本能否共存
- 配置默认值是否改变了既有行为

### 六、验证你看懂了 feature（写报告前必须完成）

1. 要写「实现与需求不符」，必须能指出具体的行为差异（输入 → 期望输出 → 实际输出）
2. 要写「边界未覆盖」，必须能指出会命中的具体路径
3. 要写「影响旧功能」，必须能指出具体的调用点/数据流

---

## 报告准则

强制项：
1. **需求覆盖度**：验收标准逐条 → 已实现/部分/未实现 + 证据锚点；注明需求基线来源。**缺的、多的（scope creep）、错的**三类分开列出，每条挂 spec 原文（issue 引用/描述原文/spec 文件:行号）
2. **实现质量**：架构合理性、与既有模式的一致性、复用与命名；没洞察就省略细节
3. **边界与错误处理**：覆盖了哪些、漏了哪些（漏的必须给具体触发路径）
4. **兼容性影响**：API/数据/存储变化的爆炸半径

按需项（有洞察才写）：
5. **认知盲区**：对需求的误解、对既有系统假设的偏差
6. **防复发建议**：最高杠杆一条（如「新功能入口应统一走 X 校验」）
