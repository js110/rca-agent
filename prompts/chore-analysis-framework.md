# Chore / 依赖分析框架（提示词模板）

目标：评估依赖升级、构建/CI 配置改动的破坏性风险。这类 PR 通常改动最小但爆炸半径最大——一个依赖版本号变了，可能影响整个代码库。
核心失败模式：版本号没变就认为无害；不看升级日志的破坏性变更列表。

---

## 调查原则

### 一、依赖升级

- 升了几个 major / minor / patch；**major 升级必查破坏性变更列表**（release notes / changelog / 迁移指南），引用原文
- 被升级依赖的调用点：新旧 API 签名差异是否被兼容
- 传递依赖变化：间接引入的版本冲突、重复打包（bundle 体积翻倍、实例不唯一）

### 二、构建 / 配置改动

- CI 脚本、打包配置、构建产物形态变化：产物内容是否改变、发布流程是否受影响
- 环境变量、权限、部署配置变化的影响面
- 移除的依赖/脚本：还有没有代码引用它们

### 三、纯文档 / 注释

- 浅析即可，标注「无行为变化」，不展开

### 四、验证你看懂了改动（写报告前必须完成）

1. 版本升级或配置改动前后，可观测行为差异是什么？声称无差异的证据是什么？
2. 被删除的配置/依赖，有没有遗漏的引用点？

---

## 报告准则

强制项：
1. **破坏性风险**：有 / 无 + 证据（升级日志原文、API 差异、调用点核对）
2. **兼容性影响**：调用点与运行时行为是否受影响；传递依赖冲突
3. **关注建议**：是否值得人工复核（如 major 升级、锁定版本移除、安全相关升级）

按需项（有洞察才写）：
4. **认知盲区**：升级时对 API 的误解（如以为 minor 无破坏性）
5. **防复发建议**：如「依赖升级必须附 changelog 摘要 + 调用点影响范围」
