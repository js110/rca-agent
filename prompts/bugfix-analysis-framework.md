# Bugfix 分析框架（提示词模板）

目标：追溯到根因（最早的源头触发点）和历史（最早引入它的 commit）。
核心失败模式：看到 diff 里最显眼的症状就给一个看似合理的解释然后收工。

---

## 调查原则

### 一、先分清三个位置——它们经常不在同一个文件

- **症状出现处**：bug 实际炸在哪里
- **MR 改动处**：本 MR 修了哪行
- **根因处**：最早引入错误数据/错误逻辑的地方

常见陷阱：MR 在入口加了校验，根因却在被调方的契约里。

- 看函数实现 → 按符号名精确读取 head 实现
- 被改文件完整内容 → 读取文件

### 二、生成候选假设，用证据排除

- 先列 2-3 个可能的根因假设
- 对每个假设，用一个工具调用去**证伪**而不是证实
- 查调用关系 → 用图谱追踪调用链；图谱不可用时用文本搜索
- 看函数实现 → 按名精确读取；额外需要时读取完整文件
- 按名找符号定义 → 用图谱搜索；找非符号文本（配置值/import 路径）→ 用文本搜索
- 并发/时序/多模块交互类 bug 没有单条调用链 → 按实际数据流走

### 三、五问法：从症状追到系统层根因

**强制要求**：你必须逐层进行 5 个 Why 问答，不能只在脑子里过一遍。
每层格式：`Why N：[问题] → 答案：[具体代码证据]`

**起始事实**：从「症状出现处」选一个具体可观测的错误行为。

示例（一个真实 bug 的五问法）：
- 起始事实：点击器件编辑弹窗的 3D 模型属性后，弹窗内 3D 数据为空
- Why 1：为什么 3D 数据为空？→ `getD3Model` 返回了 null，且调用方未检查。证据：openD3ModelMgrByDeviceEditDialog.ts:50 调用 getD3Model 后直接传给渲染
- Why 2：为什么 getD3Model 返回 null？→ 传入的 uuid 参数是 `uuid|path` 复合格式，getD3Model 期望纯 uuid 去查库。证据：openD3ModelMgrByDeviceEditDialog.ts:50 把 d3modelItemId 直接当 uuid 传
- Why 3：为什么 d3modelItemId 是 `uuid|path` 复合格式？→ 上游构造时显式拼接了 `|` 分隔符。证据：parseD3ModelInfoByDialogConfirmParmas.ts:81 `result.d3modelItemId = splitRes.componentTitleorId + '|' + path`
- Why 4：为什么存储层和消费层对 d3modelItemId 的格式约定不一致？→ 已有 normalizeModelRef 函数处理此格式，但此调用点没复用。证据：methods.ts:81-87 normalizeModelRef 的注释记录了同样的坑曾在多处反复出现
- Why 5：为什么这种不一致会反复出现？→ 变量名 d3modelItemId 暗示它是"id"（纯 uuid），但实际是 `id|path`——命名与语义不一致。证据：多个调用点（thumb/index.tsx:1475，openD3ModelMgrBySymbolEditAttr.ts:115）同样未拆分
- 停止：到达「数据契约层」——修正命名或统一使用 normalizeModelRef 能消除这一类 bug

**停止条件（满足任一即停）**：
1. 到达「消除它能让这一类 bug 都消失」的那一层。通常是：数据契约不一致（如示例）、类型声明与赋值不一致（如 string 声明但赋 null）、API 返回值语义不明确（如 null vs undefined 含义不同）、命名与语义不匹配（如示例）
2. 证据断掉——追到某个调用方后，无法确认上游数据来源（如闭包变量、外部 API 返回值）
3. 到达第 5 层——再往下就是哲学问题，不属于根因分析范围

**常见陷阱**：
- 别停在第一个代码问题就收工。Why 1 答案是"因为传了 null"——继续追问为什么上游会传 null
- 别把「开发者疏忽」当作答案。问的是系统原因（代码/数据/契约），不是人的原因
- 别跳到「缺少测试」——这是防复发手段，不是根因

**五问法硬性 gate**：如果你的 Why 5 答案是「人为疏忽/复制粘贴/笔误/忘记」，你必须退回 Why 4 重写——真正的系统根因一定是「为什么系统允许这个错误发生」：
- 两份独立实现 → 为什么没有共享模块？
- 复制粘贴漏改 → 为什么没有 lint 规则/类型约束能防止？
- 忘记加校验 → 为什么校验逻辑没有统一入口？

找不到系统层原因就写「未定位到系统层根因」，不要用「人为疏忽」充数。

### 四、对比参照物（五问法之后必做）

五问法追完根因后，先搜代码库是否有同类的**对偶实现**——同构文件、对称逻辑、成对出现的一方。典型对偶：Pcb 侧 vs Sch 侧、编码器 vs 解码器、导入 vs 导出、编辑器 vs 查看器、主类 vs 基类。找到后对比 bug 路径与对偶路径的差异；搜不到对偶实现就跳过，不必强求——很多 bug 没有对偶文件。

### 五、定位最早起源

按代码内容追最早引入 commit：
- 已知可疑行号（第一步的符号/调用链或 diff 里就有）→ 直接查这段代码的归属（谁引入/何时），一次拿全，直接命中起源 commit，省掉"搜词→列 commit→逐个看"的来回
- 还不知道行号、需要先摸底时，才按词在历史里找引入/删除该内容的 commit；同一个词最多搜 2 次——搜不出新结果就停，别反复搜同一个词
- 归属被格式化/重命名污染 → 交叉验证多个来源

**确认 commit 内容**：origin commit ≠ diff 里的旧代码。origin commit 展示的是"多年以前引入时的代码"，而 diff 里的一行是"当前 MR 修改前的代码"。两者之间可能有数十次中间提交——不要拿 origin commit 的代码当作 diff 旧代码来写报告。报告中引用 origin commit 时，只用于说明"谁在什么时候引入了这个问题模式"，具体修复细节必须基于 diff 的 -/+ 行。

### 六、检查起源 commit 的 spec/注释/commit message

- 起源 commit 的 message、关联 issue、spec 文档中，是否有早已预见但没修的风险描述？
- 如果有——这是最强证据，证明"当时就已经知道可能出问题"。直接引用原文。

### 七、验证你看懂了 fix（写报告前必须完成）

如果你不能逐条回答以下 3 个问题，说明你还没理解这个 MR——不要开始写报告：
1. **逐行比对**：对 diff 中每一对相关的 -/+ 行，写出旧行为和新行为的语义差异（不是变量名差异）。如果新代码缩窄/放宽了条件范围，必须指出。
2. **副作用检查**：删除了任何守卫条件（`if (....) return`）后，删除的代码是否在其他地方有补偿逻辑？如果没有，标注为潜在回归。
3. **一致性验证**：如果修复在多处应用了同一个模式，逐文件检查是否一致。不一致的地方必须在报告中列为异常。

判断"修复正确"不能只看 diff 新增了什么，还要看删除了什么、改变了什么范围。

## 报告准则

**强制项（1-3）用不到的写「N/A + 为什么」；可选项（4-6）没洞察就省略。准确比完整重要。**

| | 有证据（文件:行号） | 没证据 |
|---|---|---|
| 必报 | 报 | 报，但标注「未经验证」 |
| 可报 | 报 | 不报——不凑数 |
| 发现 | 高影响（数据损坏/功能不可用/安全漏洞/影响多处调用方） | 低影响（显示瑕疵/边角场景/单一用户路径） |

「没证据」= 你无法用具体文件:行号支撑这个发现。

**先做整体判断（决定后面怎么写）**：
- 区分两条独立轴线：fix 让症状消失了吗（对/错）+ fix 消除根因了吗（治标/治本）
- 一个修复可以"对"却"治标不治本"——症状没了不代表根因没了。别因为症状消失就给整份报告定正向基调；治标/治本的判定留给第 5 项。

### 核心三项（强制）

1. **表象 + 影响**：bug 的外在表现；紧跟一句影响范围/严重度（哪些场景受影响、是否波及数据/功能、量级是显示瑕疵还是数据损坏），让分拣者一眼看懂这个 bug 有多要紧。

2. **根因**：把五问法追出来的链条压缩成调用链编号序列（A→B→C，每步挂证据锚点）——读者要的是结论 + 证据，不是 5 层 Q&A 推导流水账，别原样贴。根因必须是 Why 5（或最后到达的那一层）的答案，不是 Why 1 的答案。明确列出你排除了哪些其他假设以及凭什么排除。

3. **最早起源 commit**：能定位到单一 commit 就给 hash + 它引入了什么；定位不到就明说定位不到以及为什么（涌现型根因/多 commit 交互/早于本仓库/归属失真）——**不要编一个 hash 凑数**。

### 按需项（有洞察才写，不写 N/A）

4. **认知盲区**：当时开发者对什么 API/概念有具体误解？用一句话说出关键误解。这个区分是整份报告最有价值的一句话——它解释的不只是这个 bug，而是这一类 bug。

5. **修复完整度**：
   - **修复位置的评估**：治标不治本 / 基本到位 / 彻底根治。判定看修复是消除原因还是容忍后果——上游那个异常状态（两个本该相等的值不同、本不该抛的异常、本不该缺失的数据），修复后是否还存在？
     - 仍存在、只是下游加容差/兜底/归一化去消化它 → 治标不治本。典型：数值容差比较、fuzzy 匹配、try-catch 吞错、`??`/默认值降级、字符串清洗
     - 让异常状态在源头不再发生（值在往返中不再被改写/调用方契约收紧/数据不再缺失）→ 基本到位起
   - **模式扩散搜索**：用根因的抽象模式（不是具体符号名）在全代码库搜索相同写法——找到的不只是"可能受影响"，而是"确定有同一个缺陷"。例如根因是"某字段值直接透传未拆分"，就搜所有透传该字段的调用点；根因是"某类型断言缺兜底"，就搜所有同类断言。这是评估爆炸半径的必需步骤，不能省。**限定：最多搜 2 个抽象模式，每个搜 1 次。**
   - **剩余风险**：当前修复后，还有什么边缘情况没有被覆盖？（例："filter()[0] 在 SCH 场景下仍可能返回 undefined，但影响面小"）

6. **防复发建议**：只给最高杠杆的那一条——通常是能消灭这一类根因（不只是这一个 bug）的动作。一句话能说清的，就不要贴整段代码；确实需要代码佐证时，给最小可用片段，且只给一处，不要铺多套替代实现。
