# Bugfix 分析框架（提示词模板）

目标：追溯到根因（最早的源头触发点）和历史（最早引入它的 commit）。
核心失败模式：看到 diff 里最显眼的症状就给一个看似合理的解释然后收工。

---

## 调查原则

### 一、先看懂修复：diff 逐行语义比对（追根因的前置）

没看懂这个 MR 到底改了什么，追根因只会追错方向。动手调查前，先对 diff 中每一对相关的 -/+ 行写出**旧行为和新行为的语义差异**（不是变量名差异）。如果新代码缩窄/放宽了条件范围，必须指出。这决定后面所有调查的方向。

### 二、先分清三个位置——它们经常不在同一个文件

- **症状出现处**：bug 实际炸在哪里
- **MR 改动处**：本 MR 修了哪行
- **根因处**：最早引入错误数据/错误逻辑的地方

常见陷阱：MR 在入口加了校验，根因却在被调方的契约里。

### 三、生成候选假设，用证据排除

- 先列 2-3 个可能的根因假设
- 对每个假设，用一个工具调用去**证伪**而不是证实
- 查调用关系 → 用图谱追踪调用链；图谱不可用时用文本搜索
- 看函数实现 → 按名精确读取；额外需要时读取完整文件
- 按名找符号定义 → 用图谱搜索；找非符号文本（配置值/import 路径）→ 用文本搜索
- 并发/时序/多模块交互类 bug 没有单条调用链 → 按实际数据流走

### 四、五问法：从症状追到系统层根因

**强制要求**：你必须逐层进行 5 个 Why 问答，不能只在脑子里过一遍。
每层格式：`Why N：[问题] → 答案：[具体代码证据]`

**起始事实**：从「症状出现处」选一个具体可观测的错误行为。症状来源优先级：
1. PR 描述 / 关联 issue / commit message 中描述的失败表现
2. 本 MR 伴随的新增失败测试（先读懂测试的期望再动手）
3. 以上都没有 → 从 diff 反向推断「修复改变了什么行为」，并在报告中将症状标注为「由代码推断」

**根因类别清单**（帮你收敛追问方向——真实 bug 的根因绝大多数属于以下类别，沿类别逐个对照可显著加速收敛）：
1. **数据契约不一致**：上下游对同一字段的格式/语义约定不同（复合格式当纯 id 用、null 与 undefined 混用）
2. **类型声明与赋值不一致**：声明可空却赋了空、类型收窄错误、断言缺兜底
3. **空值与边界**：空值/越界检查缺失，或检查位置不对
4. **状态未初始化/未清理**：使用前未初始化、结束后未重置、缓存未失效
5. **并发与共享状态**：共享可变状态、竞态窗口、锁顺序错误
6. **错误传播被吞**：异常被捕获后丢弃、错误分支静默降级
7. **时序与顺序假设**：依赖事件/请求顺序，而系统不保证
8. **命名与语义不匹配**：名字暗示一种语义，实际是另一种（「id」实际是「id|path」）

示例（一个真实 bug 的五问法，通用支付/订单域）：
- 起始事实：支付成功后订单状态仍显示「处理中」，发货任务不执行
- Why 1：为什么发货任务不执行？→ 发货任务只处理 status=paid 的订单，而该订单 status 仍是 pending。证据：shipment/worker.ts:42 `if (order.status !== 'paid') return`；orders 表查询结果为 'pending'
- Why 2：为什么 status 仍是 pending？→ 支付回调用回调里的 orderId 更新订单状态，但该 orderId 实际是业务单号 orderNo，与订单主键（自增 id）匹配不上，更新了个寂寞。证据：payment/callback.ts:31 用 orderId 更新 status
- Why 3：为什么回调拿到的是 orderNo 而不是主键 id？→ 支付网关回传的商户订单号被原样透传，未做转换。证据：payment/callback.ts:29 把网关字段直接赋值
- Why 4：为什么转换逻辑没被复用？→ 已有 getOrderByNo() 工具函数，但该回调是早期代码，自己重新实现了一套按单号查表。证据：payment/legacy.ts 存在重复的查询逻辑
- Why 5：为什么这种「网关字段与内部标识混用」会反复出现？→ 回调入口没有统一的参数规约层，每个支付渠道各自解析网关字段。证据：wxPay.ts / aliPay.ts 两个回调各自实现
- 停止：到达「数据契约层」——统一「网关参数 → 内部标识」的转换层能消除这一类 bug

**停止条件（满足任一即停）**：
1. 到达「消除它能让这一类 bug 都消失」的那一层。通常是：数据契约不一致（如示例）、类型声明与赋值不一致、API 返回值语义不明确（null vs undefined 含义不同）、命名与语义不匹配
2. 证据断掉——追到某个调用方后，无法确认上游数据来源（如闭包变量、外部 API 返回值、运行时环境）
3. 到达第 5 层——再往下就是哲学问题，不属于根因分析范围

**常见陷阱**：
- 别停在第一个代码问题就收工。Why 1 答案是"因为传了 null"——继续追问为什么上游会传 null
- 别把「开发者疏忽」当作答案。问的是系统原因（代码/数据/契约），不是人的原因
- 别跳到「缺少测试」——这是防复发手段，不是根因

**五问法硬性 gate**：如果你的 Why 5 答案是「人为疏忽/复制粘贴/笔误/忘记」，你必须退回 Why 4 重写——真正的系统根因一定是「为什么系统允许这个错误发生」：
- 两份独立实现 → 为什么没有共享模块？
- 复制粘贴漏改 → 为什么没有 lint 规则/类型约束能防止？
- 忘记加校验 → 为什么校验逻辑没有统一入口？

找不到系统层原因就写「未定位到系统层根因」，不要用「人为疏忽」充数。

### 五、对比参照物（五问法之后必做）

五问法追完根因后，先搜代码库是否有同类的**对偶实现**——同构文件、对称逻辑、成对出现的一方。典型对偶：导入 vs 导出、编码器 vs 解码器、编辑器 vs 查看器、读侧 vs 写侧、旧实现 vs 新实现。找到后对比 bug 路径与对偶路径的差异；搜不到对偶实现就跳过，不必强求——很多 bug 没有对偶文件。

### 六、定位最早起源

按代码内容追最早引入 commit（工具：gitBlame 查行归属、gitLog 查引入提交）：
- 已知可疑行号（前面的符号/调用链或 diff 里就有）→ 直接查这段代码的归属（谁引入/何时），一次拿全，直接命中起源 commit，省掉"搜词→列 commit→逐个看"的来回
- 还不知道行号、需要先摸底时，才按词在历史里找引入/删除该内容的 commit；同一个词最多搜 2 次——搜不出新结果就停，别反复搜同一个词
- 归属被格式化/重命名污染 → 交叉验证多个来源

**确认 commit 内容**：origin commit ≠ diff 里的旧代码。origin commit 展示的是"多年以前引入时的代码"，而 diff 里的一行是"当前 MR 修改前的代码"。两者之间可能有数十次中间提交——不要拿 origin commit 的代码当作 diff 旧代码来写报告。报告中引用 origin commit 时，只用于说明"谁在什么时候引入了这个问题模式"，具体修复细节必须基于 diff 的 -/+ 行。

### 七、检查起源 commit 的 spec/注释/commit message

- 起源 commit 的 message、关联 issue、spec 文档中，是否有早已预见但没修的风险描述？
- 如果有——这是最强证据，证明"当时就已经知道可能出问题"。直接引用原文。

### 八、写报告前的最后检查（副作用 + 一致性）

基于第一步的逐行比对结果：
1. **副作用检查**：删除了任何守卫条件（`if (....) return`）后，删除的代码是否在其他地方有补偿逻辑？如果没有，标注为潜在回归。
2. **一致性验证**：如果修复在多处应用了同一个模式，逐文件检查是否一致。不一致的地方必须在报告中列为异常。

判断"修复正确"不能只看 diff 新增了什么，还要看删除了什么、改变了什么范围。

## 报告准则

**强制项（1-3）用不到的写「N/A + 为什么」；可选项（4-6）没洞察就省略。准确比完整重要。**

| | 有证据（文件:行号） | 没证据 |
|---|---|---|
| 必报 | 报 | 报，但标注「未经验证」 |
| 可报 | 报 | 不报——不凑数 |
| 发现 | 高影响（数据损坏/功能不可用/安全漏洞/影响多处调用方） | 低影响（显示瑕疵/边角场景/单一用户路径） |

「没证据」= 你无法用具体文件:行号支撑这个发现。

**先做整体判断（决定后面怎么写）**：
- 区分两条独立轴线：fix 让症状消失了吗（对/错）+ fix 消除根因了吗（治标/治本）
- 一个修复可以"对"却"治标不治本"——症状没了不代表根因没了。别因为症状消失就给整份报告定正向基调；治标/治本的判定留给第 5 项。

### 核心三项（强制）

1. **表象 + 影响**：bug 的外在表现；紧跟一句影响范围/严重度（哪些场景受影响、是否波及数据/功能、量级是显示瑕疵还是数据损坏），让分拣者一眼看懂这个 bug 有多要紧。若症状是第一步按 diff 反向推断的，必须标注「由代码推断」。

2. **根因**：把五问法追出来的链条压缩成调用链编号序列（A→B→C，每步挂证据锚点）——读者要的是结论 + 证据，不是 5 层 Q&A 推导流水账，别原样贴。根因必须是 Why 5（或最后到达的那一层）的答案，不是 Why 1 的答案。明确列出你排除了哪些关键假设（**最多 2 个，每个一句话**）以及凭什么排除。若五问法因证据断掉而停止（停止条件 2）——写「未定位到根因」，说明断在哪一环（哪个调用方的上游数据无法确认），不要编造。

3. **最早起源 commit**：能定位到单一 commit 就给**链接**（格式：[短 hash](链接前缀/commit/完整 hash)，见系统提示词「提交链接」节）+ 它引入了什么；定位不到就明说定位不到以及为什么（涌现型根因/多 commit 交互/早于本仓库/归属失真）——**不要编一个 hash 凑数**。

### 按需项（有洞察才写，不写 N/A）

4. **认知盲区**：当时开发者对什么 API/概念有具体误解？用一句话说出关键误解。这个区分是整份报告最有价值的一句话——它解释的不只是这个 bug，而是这一类 bug。

5. **修复完整度**：
   - **修复位置的评估**：治标不治本 / 基本到位 / 彻底根治。判定看修复是消除原因还是容忍后果——上游那个异常状态（两个本该相等的值不同、本不该抛的异常、本不该缺失的数据），修复后是否还存在？
     - 仍存在、只是下游加容差/兜底/归一化去消化它 → 治标不治本。典型：数值容差比较、fuzzy 匹配、try-catch 吞错、`??`/默认值降级、字符串清洗
     - 让异常状态在源头不再发生（值在往返中不再被改写/调用方契约收紧/数据不再缺失）→ 基本到位起
   - **模式扩散搜索**：用根因的**抽象模式**（不是具体符号名）在全代码库搜索相同写法——找到的不只是"可能受影响"，而是"确定有同一个缺陷"。抽象模式 = 去掉具体符号后剩下的**行为结构**，例如：
     - 根因是「某字段值直接透传未拆分」→ 搜所有「把复合值原样透传给下游」的调用点，不限字段名
     - 根因是「回调直接消费外部字段未转换」→ 搜所有直接使用网关/外部输入的回调与入口
     - 根因是「某类型断言缺兜底」→ 搜所有同类断言
     这是评估爆炸半径的必需步骤，不能省。**限定：最多搜 2 个抽象模式，每个搜 1 次。**
   - **剩余风险**：当前修复后，还有什么边缘情况没有被覆盖？（例："filter()[0] 在某些场景下仍可能返回 undefined，但影响面小"）
   - **回归风险**（第一步副作用检查的落点）：修复删除了守卫/放宽了条件后，是否有路径失去保护？没有补偿逻辑的必须列为潜在回归。

6. **防复发建议**：只给最高杠杆的那一条——通常是能消灭这一类根因（不只是这一个 bug）的动作。一句话能说清的，就不要贴整段代码；确实需要代码佐证时，给最小可用片段，且只给一处，不要铺多套替代实现。
