# Refactor 分析框架（提示词模板）

目标：验证重构是否行为等价（重构的第一承诺）、是否真的降低了复杂度、是否夹带了不该有的行为变化。
核心失败模式：测试绿了就认为等价；新结构漂亮就忽略行为漂移。重构与 bugfix 一样要查副作用。

---

## 调查原则

### 一、行为等价性验证（核心中的核心）

- 逐文件对比重构前后的关键逻辑；抽函数/改签名时，**所有调用方是否同步**
- 改类层次时：多态分发、默认实现、基类与子类的契约是否一致
- **删除代码时（重点）**：守卫条件、默认值、兜底逻辑是否被悄悄删掉——与 bugfix 模板的副作用检查同一套标准
- 条件重构（合并/取反/提取）：真值表是否等价，缩窄/放宽了范围必须指出
- 静态字段/单例/初始化顺序变化：时序依赖是否被破坏

### 二、scope 检查

- 是否夹带行为修改/新功能（scope creep）——发现就**单独列出**，与纯重构分开评估
- 顺带修 bug：标注出来（这类「顺手修复」是重构报告最该点名的地方，因为它通常不在 reviewers 的预期内）

### 三、质量判断（重构的收益是否兑现）

- 重复是否真的减少：抽出的抽象有几个调用点？**单一调用点的抽象可能不值得**
- 新结构是否更简单：嵌套深度、圈复杂度、命名是否真实改善
- 是否过度设计：新抽象比旧代码更难懂 → 重构失败

#### Smell 基线清单（质量判断的可勾选标准，不是空话）

仓库里若有文档化编码标准（CODING_STANDARDS / CONTRIBUTING 等），**永远以仓库标准为准**——仓库标准背书的写法即使基线会标记也不报。除此之外，用下面这套基线逐个检查 diff：

- **神秘命名**：函数/变量/类型名不揭示它做什么/装什么 → 改名；起不出诚实名字说明设计本身混乱
- **重复代码**：同一逻辑形状出现在多处 hunk 或多个文件 → 提取共享结构，两处都调它
- **依恋情结**：方法访问别的对象的数据多过自己的 → 把方法搬到它依恋的数据上
- **数据泥团**：同一组字段/参数总结伴传递（一个想被生出来的类型）→ 打包成一个类型
- **基本类型偏执**：基本类型/字符串顶替了值得拥有独立类型的领域概念 → 建自己的小类型
- **重复开关**：同一个 switch/if 级联在变更中反复出现 → 用多态替换，或两处共享同一张 map
- **霰弹式修改**：一个逻辑变化迫使 diff 里散落多处修改 → 把一起变的东西收敛进一个模块
- **发散式修改**：一个文件/模块因为多种无关原因被修改 → 拆开，每个模块只为一个原因变
- **投机通用**：为 spec 里没有的需求加的抽象/参数/钩子 → 删掉，等真实需求出现再说
- **消息链**：一长串 a.b().c().d()，调用方不该依赖这个导航 → 在首个对象上藏一个方法
- **中间人**：一个类/函数大部分工作只是转发 → 砍掉，直接调真正的目标
- **拒绝遗赠**：子类忽略或覆盖了继承来的大部分 → 放弃继承，改组合

绑定规则：**每个 smell 都是带标签的启发式**（「疑似依恋情结」），不是硬违规；工具（lint/类型检查）已经强制的，跳过不报。

### 四、测试

- 重构前有测试吗；重构后测试**原样通过**（等价性的有力证据）还是被**改写**（警惕用改写测试掩盖行为变化）

### 五、验证你看懂了重构（写报告前必须完成）

1. 重构前后，同一输入的行为完全一致吗？列出你验证过的关键路径
2. 被删除的代码（if/return/默认值）在其他地方有补偿吗？没有 → 标注潜在回归
3. 声明为「纯重构」的 PR 里，有没有任何一行改变了可观测行为？

## 报告准则

强制项：
1. **行为等价性结论**：等价 / 有差异（差异点逐条列出，哪怕被证明无害，也要让读者自己判断）
2. **改动范围**：纯重构 / 夹带行为变化（列出）；顺带修的 bug 单独点名
3. **抽象质量**：重复是否真减少、是否过度设计、可维护性是否变好。命中 smell 基线清单的，点名 smell 名称 + 引用对应 hunk；每个都是判断项不是硬违规，标注「疑似」即可
4. **测试覆盖**：重构前后的测试状态、测试是否被改动

按需项（有洞察才写）：
5. **风险点**：等价性差异处的影响面
6. **防复发建议**：最高杠杆一条（如「行为变化的顺带修复应拆独立 PR」）
